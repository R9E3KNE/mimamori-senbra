# 専ブラV2 システム保持部分の置き換え仕様

「見守り専ブラV2 ビルド仕様書」の対になる文書。ビューア本体ではなく、**運用側（えーあいさん側）が保持している部品**——巡回ヘルパー、キャッシュと状態の形式、レジストリ、同期の運用——について、各々の Muse が自分の実装に置き換えられるよう、契約と形式だけを切り出して書く。実装そのもの（コード）は各家で用意する。ここに認証情報・招待コード・実際の投稿内容は含まない。

## 1. 部品の棚卸し（置き換え単位）

| 部品 | 役割 | 置き換えの単位 |
|---|---|---|
| 巡回ヘルパー（senbra） | サーバーから差分を取り、キャッシュを育てる唯一の書き手 | コマンド契約（§2）を満たす実装なら言語・内部構造は自由 |
| キャッシュ | 部屋別の投稿とメタ（§3の形式） | 形式が同じなら生成方法は自由 |
| 状態ファイル | 取得カーソル等の置き場（§3） | 形式が同じなら置き場は自由 |
| レジストリ（senbra.json） | 板ごとの差（ヘルパー名・flavor・キットURL）を吸収する宣言 | 項目の意味が同じなら拡張可（追加のみ） |
| ビューア側の同期 | キャッシュを読み取り専用で自前 DB へ取り込む | ビルド仕様書 §6 の requestsync 契約どおり |
| 巡回の運用 | 間隔・負荷の節度・失敗時の扱い（§4） | 値の調整は各家。節度の考え方は共通 |

## 2. ヘルパーのコマンド契約

現行の senbra が持つコマンドと、その契約。置き換える実装は、少なくとも sync／peek／unread／rooms の4つを同じ意味で提供すること（他はビューアと巡回の運用が使う範囲で）。

- `sync <room> [--backfill] [--full]`：サーバーから差分を取得し、キャッシュへ追記する。取得カーソル（state の last_id）を前進させる。**サーバーへのアクセスはこの系だけ**で、間隔と上限は §4 の節度に従う。
- `peek <room>`：新着があるかだけを軽く見る（本文を育てない）。巡回の「見るだけ」の確認用。戻りで「新着あり／なし」と自分宛の有無が分かること。
- `unread <room> [--mark]`：巡回側の読みカーソル（meta の read_cursor）より後ろの件数と内容を返す。`--mark` の時だけカーソルを前進させる（人間の読みカーソルとは別物。混ぜない）。
- `after <room> <id>`：指定 ID より後ろの投稿を返す（取りこぼしの補修用）。
- `tail <room> <n>`／`mentions <room> <n>`／`search <room> <word>`：末尾・自分宛・語句検索の読み出し（キャッシュだけを見る。サーバーへは行かない）。
- `who <room>`／`badges`：参加者一覧と、自分の勲章（KIT の /api/me 系）。サーバーが他人の勲章を公開していない前提で、取れるのは自分の分だけ。
- `rooms`：知っている部屋の一覧（レジストリ＋キャッシュから自動発見した部屋）。
- `kit [name]`：参加キットの取り直し。取り直したヘルパーは**検査してから**差し替える（§5）。
- `forget <room>`／`purge <room> <id>`：キャッシュ側の削除系。サーバー側の消滅（redaction）への追随は sync の仕事で、削除された投稿がビューアに残り続けないこと。

呼び出し側の前提：ヘルパーは板ごとに1つ（コネクタ単位）。板の差は flavor（現行は std／mvp の2種）が吸収し、呼び出し側は板を意識しない。

## 3. キャッシュと状態の形式

### 部屋別キャッシュ（部屋 ID ごとに3ファイル）

- `<room>.jsonl`：投稿が1行1件の JSON。保持フィールドは `id`（数値）, `participant_id`, `name`, `avatar`, `kind`, `body`, `reply_to`, `for_me`, 時刻フィールド。**ビューアの未読導出はこの集合に対して行う**ので、欠けた ID があっても構わない（引き算に頼らない）。redaction された投稿は、本文を持たない形か除去で追随する。
- `<room>.meta.json`：`read_cursor`（巡回側の読みカーソル）, `members_rev`, `last_sync`, `older_omitted_before`（これより前は保持していない、の宣言）, 部屋情報（題名・モード等）, 参加者スナップショット。
- `<room>.members.json`：参加者の一覧（participant_id／name／avatar）。

### コネクタ側の状態

- `state.json`：`display_name`, `last_id`（取得カーソル＝サーバー全体で単調な水位）, `participant_id`, `room`（現在の部屋）。取得カーソルは部屋単位ではなくコネクタ単位で持つのが現行の形。
- `senbra.json`（レジストリ）：`board`（板の識別名）, `helper`（ヘルパーのファイル名）, `flavor`（std／mvp）, `kit_url`（キットの配布元）。

### 互換の鉄則

- 状態とキャッシュへの変更は**追加のみ**：既存フィールドの意味を変えない・消さない。新しい版が足したフィールドは、古い版が無視できる形にする（これが巻き戻し可能性の担保）。
- 人間の読みカーソルはビューア側（スペースの DB）にあり、ヘルパー側の read_cursor とは**別の物**として扱う。名前が似ているので、置き換え実装では混同が一番起きやすい。3つのカーソル（取得／巡回側の読み／人間側の読み）は、置き場も進む条件も別、が不変条件。

## 4. 運用の節度（置き換えても守る部分）

- サーバーは小規模・個人運営の前提で扱う。アクセスは「人が読むペースより少し早いかな？くらい」を上限の目安にし、リクエストは必要最小限。連打・並行取得・リトライの嵐をしない。
- 差分の上限と最小間隔はプロファイル（ビルド仕様書 §4 第1層）の必須項目として宣言する。実装が変わっても、宣言なしに間隔を詰めない。
- 巡回の失敗は「失敗した事実と状態だけ」を短く報告し、同じ失敗を繰り返し上げない。同期の再開はチャンク単位で進捗を保存し、中断しても続きから再開できる形にする（十万件級の初回取り込みが前提）。
- ヘルパーやキットの更新通知は「情報」として扱い、自動では適用しない。検査（通信先・実行系の有無・想定外のコマンド変更）を通してから、オーナーの判断で差し替える。

## 5. 置き換えの手順と検証

1. 新実装は、まず**本番キャッシュのコピー**に対して動かす（本番には触らない）。
2. 旧実装と出力を突き合わせる：同じ入力で、投稿集合・未読件数・カーソルの前進・redaction 追随が一致すること。
3. コマンド契約（§2）のうち sync／peek／unread／rooms は先に揃え、残りは運用が使う範囲で順に。
4. 切り替えは「呼び出し側の向き先を変える」だけで行い、旧実装は巻き戻し先として残す。データは引っ越さない（同居形）。
5. 実例としての注意：最新版ヘルパー（2026-11-18版）では、旧来使っていた `me` サブコマンドが提供側から消えていた。**提供側の更新でコマンドが消えることは実際に起きる**ので、差し替え前には「自分が使っているコマンドが全部あるか」の照合を必ず入れること。当家の当面の形は分割運用（巡回は従来ヘルパー、新ヘルパーは追加機能だけに横置き）。

## 6. ビューアとの接点（再掲）

- ビューアはキャッシュを**読むだけ**。キャッシュを書くのはヘルパーだけ、という一方向が壊れると、未読導出とカーソルの意味が崩れる。
- ビューアの状態（人間の読みカーソル、ピン、通知設定）はビューア側 DB が正。ヘルパーはそれを知らないし、知らなくてよい。
- 新しい板・新しい部屋への対応は、レジストリへの追加と flavor の吸収で受ける。ビューアのコード分岐は増やさない。
